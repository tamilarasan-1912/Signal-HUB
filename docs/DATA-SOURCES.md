# Data Sources

Every input the platform has, what it actually provides, and what it needs to
become live.

The rule this page exists to enforce: **no value is displayed without a mode.**
`theme.js` renders an absent mode as unknown rather than defaulting to live, so
losing provenance fails visibly rather than flattering the system.

## Mode vocabulary

| Mode | Meaning | How it is rendered |
| --- | --- | --- |
| `live` | from an actual configured source, right now | green dot, "LIVE" |
| `simulated` | generated by this subsystem | amber triangle, "SIMULATED" |
| `estimated` | derived from observations rather than measured | blue, "ESTIMATED" |
| `unavailable` | the source cannot currently provide data | grey cross, "UNAVAILABLE" |
| `unconfigured` | no upstream is attached at all | grey, "UNCONFIGURED" |

Every mode is a glyph **and** a word **and** a colour. Colour alone would fail
for a colour-blind operator, and a command center that becomes unreadable for one
of its users is a defective command center.

`unavailable` and `unconfigured` are distinct on purpose: a camera that is down
is an incident, a camera that was never attached is a procurement item. Reporting
them the same way sends someone to fix the wrong thing.

## The inventory

`GET /api/data-sources` returns this list, and the **Data sources** mode renders
it. Each entry carries `keyRequired`, so an operator can see what a missing key
would cost.

### Live now

| Source | Provides | Needs |
| --- | --- | --- |
| Road geometry (Overpass/OSM) | road centre lines, classes, one-way flags | nothing — Overpass is keyless |
| Mapped ALPR infrastructure | camera **locations** only, from OSM/DeFlock | nothing |

The ALPR entry is worth reading carefully: it is **locations, not feeds, not
plate reads**. The upstream God's Eye View project already maps ALPR camera
infrastructure, and this platform reuses that layer for the map. It does not and
cannot read a plate from it, and the `detail` string says so in the API response
itself rather than only in this document.

### Live with a key

| Source | Mode with key | Mode without | What the key buys |
| --- | --- | --- | --- |
| Traffic flow (TomTom) | `live` | `simulated` | real congestion on the road network |
| Basemap imagery (Cesium ion) | `live` imagery | bundled OpenStreetMap imagery | a higher-quality basemap |

Without `TOMTOM_API_KEY` the traffic layer does not go blank. It generates a
clearly-labelled simulated flow. **It never presents simulated traffic as real**,
which is the failure mode this whole mode system exists to prevent.

### Simulated

| Source | Provides | Why it is simulated |
| --- | --- | --- |
| Traffic signals | all signal states and phases | no controller hardware is connected |
| Vehicle detection | detections, classes, confidences | no model is loaded |
| Plate recognition | plate reads with confidence | no ANPR vendor is integrated |
| Emergency vehicles | vehicles, routes, preemptions | no dispatch integration exists |
| CCTV feeds | placeholder frames and health | no camera provider is configured |

Each of these is an adapter seam. The simulation is the current adapter, not a
hardcoded behaviour — see [VISION.md](VISION.md) and
[TRAFFIC-CONTROL.md](TRAFFIC-CONTROL.md).

## Where each mode appears

Not every mode is relevant to every surface, and the UI is specific about it:

| Surface | Modes it can show |
| --- | --- |
| Road layer | `live` (Overpass) or `simulated` (fallback grid) |
| Traffic layer | `live` (TomTom) or `simulated` |
| Signal layer | `simulated` only |
| Camera layer | `simulated`, `unconfigured`, `live` if a feed is configured |
| Detection layer | `simulated` |
| Plate reads | `simulated` |
| Emergency layer | `simulated` |
| Violations | `simulated` |
| Event timeline | whatever the source event carried |
| Audit log | whatever the action's mode was |

## Behaviour when a source fails

A failed source degrades **visibly and specifically**, never silently:

| Failure | What happens |
| --- | --- |
| Overpass unreachable | labelled synthetic grid; `fallbackReason` records why |
| TomTom key absent | `simulated` traffic, labelled |
| TomTom request fails | last known values with a stale timestamp, or `unavailable` |
| Camera feed fails | explicit fallback with the reason |
| Signal controller silent | `DEGRADED` after 15 s, highlighted on the map |
| Signal controller faulted | all-red, `FAULT`, operator alert |
| Plate read below floor | `PLATE UNREADABLE`, no characters |
| Cesium ion token absent | bundled imagery, stated in the config endpoint |

The Overpass path is a good example of how this is implemented:

```js
resolveRoadNetwork({ bbox, allowLive })
// → { roads, mode, source, detail, fallbackReason }
```

A failed fetch returns `mode: 'simulated'` **and** a `fallbackReason`, and the
server starts rather than refusing to boot. The operator sees a city with a
labelled synthetic road network and a stated reason, which is more useful than a
process that will not start.

## Configuration

### Keys

| Variable | Enables | Required? |
| --- | --- | --- |
| `TOMTOM_API_KEY` | live traffic flow | no — simulated without it |
| `CESIUM_ION_TOKEN` | Cesium ion basemap | no — bundled imagery without it |
| `OVERPASS_URL` | an alternate Overpass instance | no — the public endpoint is the default |

Both keys are read **in `server/index.mjs` only**. They are never serialized into
a response and never appear in client code. The config endpoint reports
`cesiumIonToken: true/false` and `liveTrafficProvider: true/false` — booleans, not
values — so the UI can state which mode is active without the key ever leaving
the server process.

### Runtime

| Variable | Default | Purpose |
| --- | --- | --- |
| `SIGNAL_HUB_AREA` | `chennai` | area preset: bounding box, centre, zoom |
| `SIGNAL_HUB_LIVE_ROADS` | `true` | set `false` to skip Overpass entirely |
| `SIGNAL_HUB_SEED` | `7` | simulation seed |
| `SIGNAL_HUB_MAX_INTERSECTIONS` | `60` | cap on the modelled network |
| `SIGNAL_HUB_SERVE_STATIC` | `true` | serve the built frontend from the API process |
| `SIGNAL_HUB_AUTOSTART` | `false` | start the simulation loop on boot |
| `SIGNAL_HUB_STORE` | `memory` | `memory` or `file` |
| `SIGNAL_HUB_DATA_DIR` | — | required for the `file` store |
| `API_PORT` / `API_HOST` | `12001` / `0.0.0.0` | bind address |

## Persistence

| Driver | State | Behaviour |
| --- | --- | --- |
| `memory` | default | in-process records; lost on restart |
| `file` | implemented | append-only JSONL under `SIGNAL_HUB_DATA_DIR` |
| `postgres` | **not implemented** | falls back to memory *and says so* in the data-sources readout |

Asking for `postgres` does not silently succeed. The readout reports
`driver: 'memory'` with the note that the postgres driver is documented but not
implemented. A durability claim that quietly is not one is worse than no claim.

`mirrorEngineRecords({ engine, store })` subscribes to the engine's own event
bus, so the durable trail is a copy of the same events the UI shows rather than a
parallel bookkeeping path that could disagree with it.

## Entity model

Normalized for a future PostgreSQL/PostGIS port. Geometry is latitude/longitude
or WGS84 linestrings, which map onto `geography` types directly.

```text
City             id, name, area, bounds, timezone
Road             id, name, geometry, lanes, direction, roadClass,
                 intersectionIds, flow, speed, congestion, queueLength, mode
Intersection     id, name, lat, lon, approachCount, approaches[], mode
Approach         direction, vehicleCount, queueLength, avgSpeed,
                 congestion, cameraId, signalPhase, mode
TrafficSignal    intersectionId, group, phase, greenMs, startedAt, mode
Camera           id, name, lat, lon, heading, fov, feedType, provider,
                 status, intersectionId, mode
VehicleDetection detectionId, cameraId, bbox, vehicleClass, confidence,
                 at, trackId, mode
EmergencyVehicle id, type, lat, lon, heading, routeIds, etaS,
                 confidence, band, mode
Incident         id, type, severity, lat, lon, at, source, confidence,
                 affectedRoadIds, affectedIntersectionIds, response, mode
Violation        id, ruleId, cameraId, intersectionId, at, signalState,
                 trackId, evidence, reviewStatus, reviewedBy, reviewedAt, mode
Evidence         frameRef, stopLineCrossing, detectionConfidence,
                 plateResult, retainUntil
TrafficEvent     id, category, type, severity, message, at, mode, detail
SignalCommand    intersectionId, action, axis, ms, actor, role, at, outcome
SignalHealth     intersectionId, status, fault, lastHeartbeat, transitions
Rule             ruleId, description, requiredEvidence, detectionMethod,
                 confidenceThreshold, jurisdiction, reviewRequired, penalty
PenaltyConfig    ruleId, jurisdiction, effectiveFrom, penaltyAmount,
                 currency, escalationRules, reviewRequired
AuditLog         at, action, role, actor, intersectionId, outcome, mode,
                 reason, before, after
```

Two conventions worth noting:

- **Every entity carries `mode`.** Provenance is a property of the data, not
  something the UI infers from context. An entity that cannot state its mode
  cannot be rendered honestly.
- **`before`/`after` on the audit log**, not just the new value. An audit entry
  that records only the outcome cannot show whether the change was intended.

## Adding a source

1. Implement the adapter interface for its kind (detector, plate reader,
   controller, camera provider).
2. Give it a `mode`. It is required, not optional.
3. Register it; the data-sources readout picks it up from the registry.
4. If it needs a key, read it server-side and expose a boolean to the UI, never
   the value.
5. Add a row to the inventory in `engine.getDataSources()`.
